# Scope brief: where a typed judgment could touch the asset pipeline

Date: 2026-10-03. Purpose: feed a later six-face pass. Wendell's ruling of 2026-10-03 permits Jev in council and build tooling only for now, with curiosity about the asset and story pipelines later. This brief is read-only research. No TypeSafe call was made, nothing was spent, and no code changed.

Standing rules applied throughout: Jev selects, scores and verifies and never generates. Every call has a deterministic fallback. A Jev probability is a candidate and never closes a decision. Reserved items never go through Jev. No player-written text goes to a third-party model. The Portland community is wary of AI (CLAUDE.md, "Community Context").

Terms used. "Asset" has three meanings in this repo, and the brief keeps them apart: (A) uploaded media stored in Vercel Blob and recorded in the `Asset` table; (B) avatar and card art image files in `public/`; (C) the "BarAsset" game-ready BAR object in `src/lib/bar-asset/`, which is text, not media.

Not read: TypeSafe's primitive docs beyond what `.specify/specs/jev-quote-claim-check/RESULTS_2026-10-03.md` records. Whether Jev accepts image input is unverified. Everything below assumes text and application state only.

## 1. The pipeline today

### A. Uploaded media (player-facing)

1. Client picks a file. `uploadBarAsset` streams it straight to Vercel Blob with a multipart client upload, and passes `barId`, `side` and `intention` as the client payload (`src/lib/asset-upload-client.ts:24-43`). The path is `assets/{barId}/{side}/{uuid}` (`:31`).
2. The upload route checks the player cookie (`src/app/api/assets/upload/route.ts:34-39`, `:70`), requires the pathname to start with `assets/` (`:72`), requires a `barId` (`:93`), and allows only the BAR creator or an admin (`:95-105`).
3. It permits PNG, JPEG, WebP, GIF and PDF (`:30`). It declares a 5 MB image limit (`:31`) and never uses it. Only `MAX_PDF_BYTES`, 10 MB, is passed to the token (`:109`). So an image up to 10 MB is accepted. This is a code finding, verified by grep (`MAX_IMAGE_BYTES` appears once, at its declaration).
4. On completion the route inserts an `Asset` row with type `bar_attachment`, the blob URL, MIME type, an optional `{intention}` in `metadataJson`, `side`, owner and BAR id (`:113-147`), then revalidates pages (`:149-156`). The `Asset` model has no fields for alt text, licence, source, hash or review status (`prisma/schema.prisma:1349-1365`).
5. Rotation is the only later edit: `rotateAsset` writes `rotationDegrees` into `metadataJson` (`src/actions/assets.ts:130-172`, `src/lib/asset-utils.ts:2-11`).
6. Display: BAR cards render the image with `alt=""` and `aria-hidden` (`src/components/bars/BarCardFace.tsx:79-80`; also `BarFlipCard.tsx:65,103,117`, `BarPhotoForm.tsx:193`). No alt text exists anywhere in the pipeline today.
7. Other upload paths with their own limits and no shared constant: a deprecated server-action upload (5 MB images, 10 MB PDFs, `src/actions/assets.ts:12-13`); `addBarMedia` into a separate `BarMedia` table, 5 MB (`src/actions/bar-media.ts:10`, `prisma/schema.prisma:501-513`); Signal feedback images, 4 MB (`src/actions/signal-quest-media.ts:7`); Valkyrie party uploads, 8 MB, also writing `Asset` rows (`src/app/api/party/valkyrie/upload/route.ts:7-8,63-67`); book PDFs at `books/{id}.pdf` (`src/app/api/books/upload/route.ts:40`). The spec states 5 MB and 10 MB (`.specify/specs/asset-management-bar-upload-walkable-sprites/spec.md:240`). Photo and voice capture on the seed whiteboard calls `uploadBarAsset` after the BAR is created (`src/components/bars/SeedCaptureWhiteboard.tsx:1659-1676`).
8. The reason for client upload is the serverless payload limit (`src/app/api/assets/upload/route.ts:16-22`, `docs/ENV_AND_VERCEL.md:33`). No spec titled "asset budget" or "serverless assets" exists; `ls .specify/specs` and a grep for those phrases found none. The closest are `book-upload-vercel-*` and `cert-feedback-blob-persistence`.

### B. Avatar and card art files (admin and build-time)

1. Avatar layers are PNG files under `public/sprites/parts/{base,nation_body,nation_accent,playbook_outfit,playbook_accent}` stacked in that order, chosen from an `AvatarConfig` of nation, archetype and gender keys (`src/lib/avatar-parts.ts:40-99`). Code names the archetype layers `archetype_*` and maps them to `playbook_*` directories (`:56-60`). Both `archetype_*` and `playbook_*` directories exist on disk with eight files each (listing of `public/sprites/parts`), so one set may be a stale copy. Unverified which is current.
2. Admin upload accepts one PNG per layer and key, with no size, dimension or alpha check, and writes it to `public/` on local disk (`src/actions/admin.ts:711-740`). On Vercel the filesystem is not durable, so this path is effectively a local or commit-then-deploy workflow (unverified in production; the cert-feedback spec makes the same point about the runtime filesystem).
3. Validation is a script: `scripts/validate-sprite-layers.ts:1-60` checks that each PNG is RGBA and the right size (64x64 portrait layers, 512x64 walk sheets, 24x24 and 16x16 sigils). It does not check overlay-only transparency. That requirement is prose (`docs/SPRITE_ASSETS.md`, "Overlay-only requirement") with a region file `public/sprites/parts/base-silhouette.json`.
4. Quality and provenance are checklists: `docs/SPRITE_ASSETS.md` "Sprite Quality Checklist" (a human tick-list, including "Attribution documented if LPC-derived (CC-BY-SA 3.0)"). A search of the repo root and `public/` for credit, attribution or licence files found none. The sprite-generation spec lists a missing attribution file as a known risk (`.specify/specs/sprite-generation-pipeline/spec.md:104`) and proposes a `sourceModel` field (`:129`); the `Asset` model has no such field.
5. Generation: `enqueueSpriteGeneration` posts only `playerId`, nation, archetype and gender keys to a Python backend, fire-and-forget (`src/lib/sprite-queue.ts:11-48`). The spec says avatars are generated once, on acceptance, with admin review before promotion (`.specify/specs/sprite-generation-pipeline/spec.md:10-18,38-40`). `public/sprites/pending/portrait` holds one pending item.
6. Card art: a static registry of 40 nation-by-archetype entries with DALL-E prompts and a `generatedAt` field (`src/lib/ui/card-art-registry.ts:49-60`, `:538`), files at `public/card-art/` (40 PNGs on disk, confirmed by count), generated by a maintainer script and governed by `docs/CARD_ART_RUNBOOK.md`. The asset-register spec names seven visual registers and their formats (`.specify/specs/asset-register-design-system/spec.md`).
7. Carousel: `raise-awareness-carousel-forge` is browser-only. A steward pastes approved text and exports 1080x1080 PNGs; "No data leaves the browser" and no AI call (`.specify/specs/raise-awareness-carousel-forge/spec.md`, MVP boundary and Acceptance criteria). Out of scope for any model call as written.

### C. BarAsset (text object)

1. A BarSeed at maturity `shared_or_acted` or above is translated to a BarAsset at `integrated`; lower maturity throws (`src/lib/bar-asset/translator.ts:96-105`, `PROTOCOL.md` "Maturity Protocol").
2. The translator already sends the BAR's text to a generative model through `dispatchAI`, temperature 0.8 (`translator.ts:111-116`), which picks Zo, Anthropic or OpenAI from environment keys (`src/lib/bar-asset/providers.ts:30-35`). This is existing generative use on player prose. It is outside this brief's rulings and is flagged in section 3.
3. Persistence upserts a `CustomBar` row (`src/lib/bar-asset/persistence.ts:32-60`). The feedback loop turns play data, which can include player text, into BarAssets (`src/lib/bar-asset/feedback-loop.ts:1-40`, `play-data.ts:1-13`).

## 2. Candidate typed judgments on non-personal asset data

Honest summary first: most asset decisions here are format or arithmetic, where a deterministic rule is cheaper, exact and offline. Jev adds something only where the input is a short text description and the rule would be a judgment about meaning. Rows are ordered by how much room Jev has.

| # | Decision | Primitive | State it would contain | Deterministic fallback | Cost of a wrong answer |
|---|---|---|---|---|---|
| 1 | Does a doc or spec statement about assets agree with the code it describes (layer names, size limits, upload paths)? Build tooling. | Choice: agrees, contradicts, silent | The doc sentence and the code excerpt, pairwise | Exists: a human reads both, as today. A grep for the constants handles the numeric cases | A missed contradiction keeps a stale doc. A false flag costs a reader a minute. Low |
| 2 | Is an admin's provenance note for a sprite enough to meet the licence checklist (source named, licence named, attribution stated)? | Choice over the three checklist items, or one Noul per item | The admin's free-text note and the checklist wording. No image | Needed: a required structured field (source, licence, attribution URL) and a presence check. With the field, Jev adds little | A missed gap leaves a CC-BY-SA sprite without credit. Real but slow-moving legal risk. Jev must never pass it |
| 3 | Does a card-art or sprite prompt in the registry or `SPRITE_ASSETS.md` state the style contract (palette, outline, transparency, region)? | Score along "completeness of the style contract" | The prompt text and the style guide | Exists in part: string checks for the hex values and the phrases "transparent background" and "1px black outline" | Low. A weak prompt wastes a generation run |
| 4 | Is a sprite file name and layer pairing sensible (right key for the layer)? | Choice from the defined set of keys | File name, layer, the expected key list from `getAdminSpriteAssets` (`src/actions/admin.ts:676-709`) | Exists: the key list lookup | Low, and exact matching beats Jev |
| 5 | Which category an uploaded asset belongs to (attachment, party media, signal feedback) | Choice | MIME, path prefix | Exists: the `type` and path prefix are set by the route | None needed. The category is known at upload |
| 6 | Budget classification: does a file fit its path's limit | none | size, type | Exists in arithmetic. Jev has no role | Not a Jev decision. The finding is the unused 5 MB constant (section 1, A3) |
| 7 | Near-duplicate or duplicate | none | image bytes | Perceptual hash or byte hash with `sharp` (already a dependency, used in `scripts/validate-sprite-layers.ts:20`) | Jev cannot see pixels as far as verified, so it has nothing to judge |
| 8 | Overlay-only transparency and registration | none | pixels | Pixel test against `base-silhouette.json` regions with `sharp`. Cheap and exact | Currently a human reads it. A script would beat Jev here |
| 9 | Alt-text presence and fit | none today | no alt field exists | Needed first: an alt-text field and a presence check | Jev could later score whether an author-written alt text describes an author-written caption. Both would be player text on BAR images, which is out of reach (section 3). For admin art (card art, sprites) the alt text would be council-written, so Jev could score it, but Jev must not write it |
| 10 | Tag or route a BAR photo by its `intention` text | Choice | the `intention` string | Existing manual reading | Out of reach. `intention` is player-written (section 3) |

Rows 4 to 8 are listed so the six-face pass can rule them out explicitly. Rows 1 to 3 are the only ones where the input is non-personal text and the judgment is about meaning.

## 4. Ranked shortlist of first trials

Only trial 1 has a labelled set in the repo. No set of human-labelled asset tags, categories or licence verdicts exists, and none is invented here.

**Trial 1. Asset doc-versus-code agreement (row 1).**
- Test: for each asset statement in a fixed list of docs, ask Jev for a three-way Choice against the code excerpt, and compare to a baseline of a constant-extraction script for numeric claims. The test can fail in two ways: Jev misses a known contradiction (recall below the pass mark Wendell sets), or Jev flags more than a reader can clear in the time the manual pass takes.
- Existing labelled set: five known drifts found in this brief, each with its doc line and code line. (a) The upload route declares 5 MB for images and enforces 10 MB (`route.ts:31` against `:109`). (b) The spec says 5 MB images and 10 MB PDFs (`spec.md:240`) while Signal media allows 4 MB (`signal-quest-media.ts:7`) and Valkyrie 8 MB (`valkyrie/upload/route.ts:8`). (c) The sprite doc and validator say `playbook_*` while code types say `archetype_*` (`validate-sprite-layers.ts` rules, `avatar-parts.ts:56-60`). (d) `docs/SPRITE_ASSETS.md` lists "Attribution documented if LPC-derived" as a checklist item with no attribution file in the repo. (e) The sprite spec proposes a `sourceModel` field the `Asset` model lacks (`spec.md:129` against `schema.prisma:1349-1365`). Five positives are too few to measure a rate. They are enough to see whether Jev finds known cases. Negatives (statements that agree) would have to be labelled by a person. Unverified: a complete list of asset doc statements; it must be built.
- Cost: low. A script of roughly the size of the quote-to-claim script, and the same equal-information rule, in the council tooling folder, with no player data.

**Trial 2. Prompt completeness against the style contract (row 3).**
- Test: Jev Score on the 40 registry prompts and the 26 prompts in `SPRITE_ASSETS.md` for "states the full style contract". Pass only if Jev's low scores match the deterministic string check's failures and add at least one case a person confirms the string check missed. If it adds none, the string check wins and the trial ends.
- Existing labelled set: the string check itself, which is deterministic and exists in spirit but not as a script. Unverified: how many prompts fail it today. The registry builds prompts from five element functions (`card-art-registry.ts:269-461`), so the 40 are near-identical templates and give little variation to measure. Weak trial.
- Cost: low to medium. Needs the string check written first, which is the useful part.

**Trial 3. Provenance-note sufficiency (row 2), only after the structured field exists.**
- Test: with a source, licence and attribution field in place, Jev checks whether the free-text note beside it is consistent with the fields. It must never pass an asset; a low score only sends it to a person.
- Existing labelled set: none. The repo has no sprite provenance notes to label. Do not start until Wendell decides whether admin sprites are in scope (section 5, Q3).
- Cost: medium. A schema change on `Asset` or a sidecar file, a migration under the repo's migrate-only rule (`docs/PRISMA_MIGRATE_STRATEGY.md`), and an admin form.

What I would build before any of them, with no Jev: a pixel-level overlay check (row 8) and an upload-limit constant shared by all upload paths (row 6). Both are deterministic and remove two of the five known drifts outright.

## 5. Open questions only Wendell can answer

1. Does the "asset pipeline" curiosity mean admin art (sprites, card art) only, or also player uploads? Option A, admin art only: every trial above stays in reach, and player media stays closed. Option B, include player uploads: nothing in section 3 can go to Jev under the standing rules, so this would need a rule change, and the repo gives no basis for one. This is a scope decision about trust, so the repo cannot answer it.
2. Are the card art images, their DALL-E prompts and the lore strings in the registry reserved as canonical prose, or are they build material? If reserved, trial 2 loses its input. If not reserved, it can run. The repo says the images are "canonical" (`docs/CARD_ART_RUNBOOK.md`) without saying whether that engages the council's reserved list. This is Wendell's list.
3. Is LPC-derived or AI-generated sprite licensing a live concern now? Consequence if yes: a structured provenance field and an attribution file come first (the repo has neither), and trial 3 becomes worth building. If no: drop trial 3 and keep the two build-first items. The repo shows the checklist item and the spec's risk line, and no evidence of which assets are LPC-derived.
4. Does the Python sprite backend call a third-party image model, and with what data? `enqueueSpriteGeneration` sends player id and keys to `BACKEND_URL` (`src/lib/sprite-queue.ts:21-34`). The backend code is not in this repo as far as I searched. Option: Wendell confirms the backend is first-party and sends no player text; consequence if it is not, a rule collision to rule on. Unverified.
5. Is the BarAsset translator's generative call (`translator.ts:111-116`) live, and is it acceptable beside the no-player-text rule? Options: leave it, gate it behind an opt-in, or retire it for a non-AI translator. The repo shows the code and not its production use.
6. Does Jev accept images, or only text and state? I did not read TypeSafe's image documentation, and the quote-claim results file records no image statement. If Jev takes images, rows 7 and 8 and sprite style checks reopen, though the non-personal admin art would be the only eligible set. Wendell or a read of docs.typesafe.ai would settle it; I was told to make no API calls and did not browse the docs.
7. What pass mark and sample size count as success for trial 1? The brief gives no numbers because the repo holds none for assets. The quote-claim spec left its own numbers open for the same reason.
